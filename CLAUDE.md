# Where's the Bottom? (Hot Attic Games): standing project rules

- **Studio splash is mandatory.** Every Hot Attic Games app/game opens with the studio splash before its own title/menu, on every cold launch. The canonical artwork is exactly `Hot_Attic_Games_Master_Logo_ALPHA_FINAL.png` (repository root). Never redraw, substitute, crop, distort or edit it; the old `branding/Hot_Attic_Games_Master_Logo.png` path is obsolete. Details and how it is built here: docs/studio-splash.md.
- **Public version.** Releases are named `Where's the Bottom? v<number>`; `release.json` is the only place the number is edited. OTA #, versionCode, runtime, SHA stay internal. docs/release-naming.md.
- **Owner is not an engineering stop-gap.** Kevin judges feel, fun, mechanics and physical-device behaviour; Claude completes all other engineering, qualification and release preparation on isolated branches. Never publish an OTA/release or merge a held PR without explicit authorization; never expose or commit signing material; never risk the installed save (docs/signing-continuity.md, docs/save-protection.md).
- **Page size.** The game is one inline HTML string that fails (black screen) above ~10 MB on Android; keep `dist/index.html` under the 7.5 MB budget in `eas-update.yml`.
- Checks before any push: `npx tsc && npx eslint . && npx vitest run && python3 -m unittest discover -s scripts/tests`, and `npm run test:smoke` for UI changes.
- **GitHub Actions budget (standing owner directive).** Actions minutes are shared across projects and deliberately small. Before starting any hosted workflow ask: "Does this need GitHub Actions, or can I prove it locally?" Validate locally first (tsc, eslint, vitest, python tests, `npm run test:smoke`, page-size check). Use Actions only for final candidate validation near release/OTA, tests that cannot be run locally, an APK/AAB the owner actually needs, OTA publication with its safety gates, and release builds. Never for: builds after every push, artifacts for OTA-only/doc/bookkeeping changes, re-running to see if a flaky test passes, rebuilding the same SHA when a verified artifact exists. Docs-only commits to a workflow-triggering branch carry `[skip ci]`. Never skip signing, runtime/OTA compatibility, ancestry/rollback or other release gates to save minutes. Details and the audit: docs/actions-budget.md.
- **ONE authoritative history (permanent engineering policy).** Every change belongs to one product history; every supported platform builds from it; every abandoned branch is accounted for before valuable work is discarded. One codebase does not mean one binary: platform differences live in isolated, documented shells/adapters, never in a forked copy of the game. Branches are temporary workspaces that start from the authoritative line (`authoritative.json`) and are integrated after validation; never delete a branch because it looks obsolete. Release builds must contain the authoritative baseline (`scripts/assert-release-source.mjs`), every artifact gets a provenance manifest, and a multi-platform release uses one SHA for all targets (`scripts/make-release-manifest.mjs --check-parity`). Unmerged work stays visible: update `docs/branch-ledger.json` and run `node scripts/branch-inventory.mjs --check` (local) when creating or retiring a branch. Details: docs/architecture.md, docs/branch-ledger.md.
- **Publishing is never automatic (release authorization).** No push, merge, PR, tag, version bump or docs change may publish an OTA, GitHub Release or signed build; no `[skip ci]` reliance. Publishing workflows (`eas-update.yml`, the `release` job of `eas-build.yml`, `release-android.yml`) are dispatch-only, need the exact approved 40-character SHA, a typed confirmation word and the `production-release` environment, and verify the SHA (`scripts/verify-approved-source.mjs`: checked-out HEAD == approved SHA, contains the baseline, on the authoritative line). Agents never dispatch them without explicit owner approval. Procedure and promotion order: docs/release-authorization.md. Do not add push/tag/release/workflow_run triggers to a publishing workflow; `src/test/releaseAuthorization.test.ts` fails if you do.
