# One product, one history, many targets

Permanent engineering policy (CLAUDE.md summarises it; `src/test/singleSource.test.ts` enforces what can be enforced).

**We are developing ONE GAME that runs on Android (and any future target).** Not an Android game plus a Windows game. One authoritative codebase, one integrated history, multiple build targets, no silent platform divergence, no forgotten completed work.

## Authoritative line

`authoritative.json` names the line and its baseline commit (the source of the live release). Today: branch `claude/repo-gameplay-review-loq9rq`, baseline `41c8cfb` (OTA #83). Every release build (APK, AAB, and by the OTA ancestry guard every OTA) must contain that baseline. Advance the baseline only when a newer line has actually shipped. `main` (the default branch) is 82 commits behind and carries disabled publish stubs; integrating the authoritative line into it is an owner decision (docs/branch-ledger.md).

## Targets from one source

- Shared game: `src/` (physics, economy, tricks, saves, UI), built by Vite into one HTML bundle. This is the same bundle in the browser test harness (`npm run test:smoke`), in an OTA and in the APK.
- Android shell: `App.tsx` + Expo native project (generated by `expo prebuild`; `android/` is never committed). Platform-specific seams are isolated: the WebView bridge (`window.ReactNativeWebView`), update gate/status (`src/shell`), Back handling, haptics, music streaming. Differences are documented where they live.
- A new target (for example Windows) must reuse `src/` and add only its own shell/packaging; it does not get a copy of the game. Supported platforms are listed in `authoritative.json`.
- A fix made for one target is evaluated against every supported target before it is considered done.

## Branches are workspaces

Feature, repair and agent branches must start from the authoritative line, have a stated purpose, and be integrated after validation. They are never separate products, and platform names in a branch name grant nothing. No branch is deleted because it looks obsolete. Unmerged work stays visible:

- `docs/branch-ledger.json` accounts for every remote branch that holds commits not on the authoritative line (not patch-equivalent to one that is). Human-readable form: docs/branch-ledger.md.
- `node scripts/branch-inventory.mjs --check` (local, free) fails when a branch has unaccounted work or a reviewed branch moved. Run it before a release and whenever a branch is created or retired.

## Releases and provenance

- Release workflows refuse a source that does not contain the baseline (`scripts/assert-release-source.mjs`, full history required; a shallow clone fails visibly, it never skips).
- Every build writes `<artifact>.manifest.json` (`scripts/make-release-manifest.mjs`): source SHA and ref, public version, platform, package id, app/runtime version, versionCode, build configuration (variant, signing), CI run, build time, toolchain/dependency versions, artifact SHA-256s.
- A coordinated multi-platform release uses ONE approved SHA for every target: `node scripts/make-release-manifest.mjs --check-parity a.manifest.json b.manifest.json` fails on a different source SHA or public version. If one platform fails validation, fix it on the same SHA or move every platform to a new SHA; never substitute a different revision for one platform.
- OTA vs native: unchanged. `release-route.sh` classifies each change; the runtime version (app version) must be bumped for native-capability changes; OTAs carry their source commit in the manifest (`app.config.js` `extra.ota`) and are guarded by "never go backwards".
- CI cannot pass by skipping: no `.skip/.only` tests (tested), the keytool-dependent signing tests must run in CI, the APK gate fails closed without its tools.

## What this does not change

Gameplay feel, physics, features, visual identity, save formats and published identifiers (`com.hotatticgames.snow`), working OTA compatibility and signing are untouched by this policy.
