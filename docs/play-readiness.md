## Current Google Play requirement

Source (read 2026-10-03): https://developer.android.com/google/play/requirements/target-sdk

## Remediation class: CLASS B (substantial stack migration). NOT PERFORMED.

STOPPED for owner instruction. No dependency was touched.

- Current stack / API: Expo SDK 51, React Native 0.74.5, targetSdk 34, AGP 8.2.1, Gradle 8.6.
- Required: targetSdk 36 (and the Play 16 KB native-library alignment requirement, which RN 0.74's prebuilt native libraries do not meet).
- Why the current stack cannot comply: React Native 0.74 / Expo 51 are built and tested against compileSdk/targetSdk 34 and AGP 8.2; Android 16 APIs and 16 KB page alignment need a newer AGP/Gradle/NDK and a React Native release that ships aligned libraries (RN 0.77+ line; Expo SDK 53/54 or newer).
- Minimum migration: Expo SDK 51 → a current SDK (several majors), React Native 0.74 → matching release, react-native-webview, expo-updates, expo-constants, expo-screen-orientation, expo-status-bar, expo-asset to matching versions; AGP/Gradle/JDK/NDK updates; config-plugin and prebuild changes; likely New Architecture becoming the default/only path.
- Likely affected: package.json and lockfile, app.json, App.tsx (expo-updates and WebView APIs), the native shell behaviour (`onRenderProcessGone`, orientation, back handling), `eas-build.yml` toolchain, `release-route.sh` classification.
- OTA consequences: a new runtime version (bump `expo.version`) and a mandatory new APK/AAB. Installed runtime-0.0.1 builds keep receiving runtime-0.0.1 OTAs and cannot receive the new runtime. A safe cut-over keeps the old line alive until testers move.
- Save/data consequences: game data is IndexedDB inside the WebView. Keeping the same package ID AND the same signing key keeps it on update. The debug keystore note below matters here.
- Build consequences: new runner toolchain, cache invalidation, a first prebuild that must be diffed against today's output.
- Testing consequences: full physical retest (WebView rendering, audio, touch, back, orientation, update/rollback), plus the full automated suite.
- Scope and risk: medium-large; the main risk is the WebView/Babylon runtime and expo-updates behaviour changing together.
- Recommended approach: a dedicated migration branch from the live line, one SDK step at a time using Expo's upgrade path, each step building an APK in Actions and smoke-tested on a device; no half-converted state on the live branch.
- Alternative: stay on 0.0.1 for owner testing outside Play (APK sideload) and migrate before Play internal testing. The 2026-11-01 extension can be requested if Play upload is imminent.
- OWNER DECISION REQUIRED: go/no-go and timing (see the end of the execution report).

## Signing: DEBUG (not production)

`eas-build.yml` builds `assembleRelease` with the Expo template's debug keystore (no secrets wired). Consequences:
- Fine for sideload testing; NOT acceptable for Play. Play needs an upload key (and Play App Signing).
- Switching keys later forces testers to uninstall (the signature changes) and loses local saves, as the workflow header already warns. Choose the final upload key BEFORE wider testing.
- Production signing must read named secrets and fail hard when absent. It is not wired yet. Never commit key material. OWNER owns custody.
